## Product Brief (Draft — pending review)

- Public users do not sign in. They may submit one client record containing client name, company name, telephone number, email, and submitter name; they cannot edit or resubmit that record.
- Public users may upload supporting documents, such as reports. Submitted records and documents are publicly viewable and downloadable.
- The public directory needs search and filtering, initially by category and other relevant metadata.
- Admin users must sign in. They can edit client name, telephone number, and email.
- Intended production stack: Next.js, TypeScript, React, Tailwind CSS, Next.js Route Handlers, Supabase, and Vercel.

## Design Direction (Draft — pending approval)

- Direction: “Calm Safety Intelligence” — a premium, credible public information hub rather than a generic corporate portal.
- Visual reference mix: Linear’s focused, efficient product surfaces; Vercel’s high-contrast confidence; and Stripe’s editorial hierarchy and carefully framed content.
- Palette: warm off-white base, deep navy ink, safety teal as the primary interactive color, and amber only for status/attention.
- Motion should be brief and purposeful: responsive hover/focus feedback, route and panel entrances, filter/list updates, and success confirmation. Respect `prefers-reduced-motion`; no distracting continuous animation.

## Accessibility audit (2026-10-05)

A real audit-and-fix pass (not a fixed deliverable) across public pages and admin. No screen reader/real browser available in this environment, so verification was code-level (computed WCAG contrast ratios directly from the actual hex tokens, confirmed component wiring/compiled CSS output) rather than visually observed — flagged explicitly per finding below.

**Found and fixed, real issues (not theoretical):**
- **`--ink-faint` failed WCAG AA almost everywhere it was used.** Computed actual contrast ratios from `globals.css`'s hex values: light mode was 2.93:1 against `--surface` (needs 4.5:1 for normal text), dark mode 3.43:1. This token is in heavy use as real label text — KPI tile labels, admin table headers, section headers like "MONTHLY BREAKDOWN", step labels on the submit form — all at 10-12px, none large enough to qualify for the relaxed 3:1 "large text" threshold. Fixed by adjusting the token itself (not individual call sites, so every usage is fixed at once): light `#8a9a98` → `#5c716f` (5.19:1/surface, 4.87:1/canvas), dark `#5e7573` → `#7c9a97` (5.57:1/surface, 6.15:1/canvas). Trade-off disclosed: this brings `ink-faint` visually close to `ink-muted` — an inherent tension, since a genuinely "faint" light-gray tone cannot pass 4.5:1 against a near-white background. Chose "both tones accessible but visually similar" over "clearly distinct but one illegible."
- **`--amber` on `--amber-soft` also failed** (3.69:1, used for the "Before you submit" notice and category badges at 10-12px, no large-text exemption applicable). Darkened light-mode `--amber` from `#b86a00` to `#955400` (5.31:1). Dark mode was already fine (7.44:1), untouched. Confirmed via grep that `text-amber` is never used against any background other than `amber-soft`, so this was safe to adjust globally.
- **`<html lang="en">` was hardcoded in the root layout**, which also wraps the `/ms` (Malay) pages — every Malay page was telling screen readers and browsers it was English. Root cause: the root layout is deliberately locale-unaware (shared by both the i18n public tree and the English-only admin tree, an earlier architecture decision), so it has no way to know the active locale at that level. Fixed with a small client component, `src/app/_components/html-lang-sync.tsx`, mounted in `src/app/[locale]/layout.tsx` (where the locale **is** known) — reads `useLocale()` and sets `document.documentElement.lang` via `useEffect`. **Disclosed limitation**: this is a post-hydration fix, so the server-rendered HTML still briefly shows `lang="en"` before JS runs (confirmed via curl — expected, not a bug) — correct in any real browser almost immediately, but I can't verify the actual post-hydration DOM value without a real browser in this environment.
- **Destructive delete-confirmation in admin had no live-region announcement** — clicking "Delete" on a client card swaps in a "Delete this client and all its documents?" prompt with no `role="alert"`, so a screen-reader user wouldn't be told it appeared. Added `role="alert"` to that element (`admin-clients-table.tsx`), matching the pattern already used for form error messages elsewhere.
- **Two dropdown search inputs (command palette, category filter) had `outline-none` with no compensating visible focus state** — unlike every other input in the app, which uses `focus-within:ring-*` on a wrapper. Added `focus-within:bg-accent-soft/30` to both wrapper divs for a visible, consistent focus indicator. Also added explicit `aria-label` to both `Command.Input` elements — they were relying on `placeholder` alone as their accessible name, which is a known anti-pattern (placeholder text isn't a reliable substitute for a label across screen readers).

**Checked and found already correct, not touched:** heading hierarchy on every page (clean h1→h2→h3 nesting throughout); icon-only Edit/Delete/admin-nav buttons (all have visible accompanying text, not actually icon-only); `BrandLogo` (has both `aria-label` on the link and `alt` on the image); the realtime toast banner (already `role="status" aria-live="polite"`); the command palette dialog (already has an accessible `label` prop); all generated `<img>` tags for icons/OG-image (correctly `alt=""`, decorative, not content-bearing).

## File-size limit fixed to match Vercel's real 4.5MB cap + automatic PDF compression (2026-10-06)

- Kay hit "We could not reach the submission service" uploading a real audiometry PDF on the live site. **Diagnosed precisely, not guessed**: Vercel enforces a hard, non-configurable 4.5MB request-body limit per serverless function (`413 FUNCTION_PAYLOAD_TOO_LARGE`), confirmed by directly testing a small file (succeeded) and a 6MB file (failed with exactly that error) against the live `/api/submissions` endpoint. Our own app-level limit was `10 * 1024 * 1024` — a ceiling Vercel would never actually honor, so anything between ~4.5MB and 10MB silently failed with a confusing generic network error instead of a clear message.
- **New real limit: 4MB** (`4 * 1024 * 1024`), set in both `src/app/api/submissions/route.ts`'s `MAX_FILE_SIZE` (authoritative) and mirrored client-side in `submit/page.tsx` (same constant, pre-checks before even attempting upload) — leaves ~500KB headroom under Vercel's actual 4.5MB ceiling for the other form fields/multipart overhead.
- **New client-side PDF compression** (`src/lib/compress-pdf.ts`, new dependencies `pdfjs-dist` + `pdf-lib`) — when a selected PDF exceeds 4MB, it's automatically re-rastered: each page rendered to a canvas via `pdfjs-dist` at a fixed scale, re-encoded as JPEG at decreasing quality steps (0.7 → 0.5 → 0.35) via `canvas.toBlob()`, then reassembled into a new, smaller PDF via `pdf-lib`'s `PDFDocument.create()` + `embedJpg()`. Stops as soon as a quality step fits under the limit. Both libraries are **dynamically imported inside the compression function** (not top-level), so neither lands in the main page bundle — only loaded when someone actually picks an oversized PDF. Verified the exact `pdfjs-dist@6.4.299` `render()` API (`canvas`/`canvasContext`/`viewport` params) against its real bundled type definitions before writing this, rather than assuming from general knowledge, since this library's render signature has changed across major versions before.
- **Deliberate, disclosed scope boundary**: DOC/DOCX files have no reasonable client-side compression path — if one exceeds 4MB, the user gets an immediate clear rejection (`FILE_TYPE_CANNOT_COMPRESS`) asking them to reduce it manually or convert to PDF, rather than a silent failure. Same clear-message treatment if a PDF still doesn't fit after all compression attempts (`FILE_TOO_LARGE_AFTER_COMPRESSION`).
- UI: file picker shows a "Compressing your document…" state (dropzone dimmed/disabled) during compression, then a small transparency note ("Compressed from X MB to Y MB") once done, since the swap is lossy and shouldn't be silent. New i18n keys in both `en.json`/`ms.json`: `submit.compressing`, `submit.compressedNotice`, `submissionErrors.FILE_TOO_LARGE_AFTER_COMPRESSION`, `submissionErrors.FILE_TYPE_CANNOT_COMPRESS`; `submit.fileHint` and `submissionErrors.FILE_SIZE` updated from "10 MB" to "4 MB".
- **Verified what's verifiable without a real browser**: build/lint clean; server-side 4MB enforcement confirmed live (a 5MB PDF correctly gets `400 FILE_SIZE` even if somehow sent directly, bypassing the client); a small file still submits normally end-to-end. **Disclosed limitation**: the actual canvas-rendering/JPEG re-encoding compression logic itself can't be exercised in this environment (no browser/DOM/Canvas) — Kay needs to try a real oversized PDF in an actual browser to confirm the compression path works as designed, not just that the size-gating logic around it is correct.
